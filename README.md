# 九爺，我想給您養老

《極目不見故土2》的實體活動互動系統，分**主持人端**與**玩家端**。
固定 7 名角色的故事＋機制陣營本，所有資料 100% 記錄在 **Google Sheet**：
每開一場（一個日期）就在試算表裡長出當天專屬的分頁作為工作資料庫。

## 手機版介面

主持人與玩家都用手機，所以兩端都是**固定框架＋底部導覽列**，而不是長捲頁：

```
┌──────────────┐
│ 固定 header    │  場次、階段、狀態
├──────────────┤
│              │
│  內容（自己捲）  │  只有這一區會捲動
│              │
├──────────────┤
│ 固定操作區      │  主持台「調配」分頁才有
├──────────────┤
│ 底部導覽列      │  永遠在拇指構得到的位置
└──────────────┘
```

**玩家分頁**：我的／榜單／舉報／角色／動態
（「舉報」只在第一～三週出現，其餘階段自動隱藏）

**主持分頁**：調配／階段／舉報／設定／紀錄
（「舉報」分頁有待判定數量的紅點提示）

主持台的「調配」分頁把玩家列表放在可捲區、資源與加減按鈕固定在底部，
所以點選玩家後可以直接按 +10，全程不需要捲動。

版面用 `100dvh`（會隨手機網址列收合調整，比 `100vh` 準確）與
`env(safe-area-inset-bottom)`（避開 iPhone 的 home indicator）。

> 內容多的列表（紀錄、玩家清單）由中間區塊自己捲動，
> 外層頁面永遠固定——這樣導覽列不會被推走，也不會被虛擬鍵盤蓋住。
> UI 測試會逐一切換 10 個分頁，斷言整頁不捲動且導覽列可見。

## 數值可見性規則

這是最容易寫錯、寫錯又最難發現的部分，所以獨立說明：

| 數值 | 本人 | 其他玩家 | 主持人 |
|---|---|---|---|
| **勢力值** | 看得到數字 | **只看得到名次，看不到數字** | 全部看得到 |
| **威望值** | 看得到數字 | 看得到數字（公開排行榜） | 全部看得到 |
| **血量** | 看得到數字 | 看不到 | 全部看得到 |
| **真實陣營** | 看不到 | 看不到 | 只有主持人看得到 |
| **招募次數** | 看得到自己的 | 看不到 | 全部看得到 |
| **隱藏分支** | 看得到自己的 | 看不到 | 全部看得到 |

實作上不是「前端不顯示」而是**後端根本不傳**：
`/api/sessions/[code]/state` 依身分回傳不同結構，玩家拿到的 JSON 裡
連其他人的 `power` 欄位都不存在。這支端點因此必須驗證身分，不接受匿名讀取。

### 動態（流水帳）的可見性

玩家在動態裡**看不到任何別人的數值變動**，連威望值都不行。

威望值在榜單上是公開的，但動態出現「某某 威望值 −1」就等於公布他被舉報成立、
或被技能卡構陷了，而依規則「公布時不顯示明細，只顯示數字的結果」。
招募次數同理——次數由威望排名決定，公開等於把排名攤開講。

**當事人看得到自己的每一筆**——被構陷、舉報結算被扣威望，本人一定看得到，
只是看不出是誰做的、也看不到事由（結算那筆的事由與來源都留白）。

別人的紀錄只有這幾種看得到，而且不能夾帶數值：**入場、被移出場次、聘書**。
這些現場本來就看得見。

`source`（來源類型）在玩家端一律清空。玩家介面從來不顯示它，留在 JSON 裡
只會洩漏「這 −1 是舉報來的」這種依規則不該公布的明細。

實作在 `visibleToPlayer()`，用**白名單**而不是黑名單：
之後新增紀錄類型時，預設就是「別人看不到」，忘了設可見性也不會外洩。
主持台不受影響，仍保有完整的帳。

### ⚠️ 機密資料不能放進玩家端會 import 的模組

「後端不傳」只擋得住 API。還有第二條外洩管道：**前端 bundle**。

`src/lib/characters.ts` 會被玩家端的 client component import，
裡面所有東西都會原封不動打包進瀏覽器下載得到的 JS。真實陣營一度被放在這裡，
結果玩家打開 devtools 就能看到全場陣營——API 一個字都沒多傳，但遊戲已經破功。

所以：

| 資料 | 放哪 | 玩家端怎麼拿 |
|---|---|---|
| 角色姓名、難度、性格、海報 | `src/lib/characters.ts` | 直接 import，本來就公開 |
| **真實陣營** | `src/lib/script-factions.ts`（只有伺服器端 import） | 拿不到，本來就不該拿到 |
| **21 張線索卡答案** | `characters.ts` 的 `CLUE_CARDS`，但只有伺服器端引用 | 靠 tree-shaking 排除，**不要在 client component 引用它** |

主持台要顯示「劇本原訂陣營」時，走 `HostSnapshot.scriptFactions` 由伺服器帶下來，
不要在前端 import 機密檔案。

改完記得驗一次：

```bash
npm run build:only && npm run check:leaks
```

`scripts/check-leaks.mjs` 會掃玩家端的 chunk，找角色→陣營的對應與線索卡編號，
發現就讓 CI 掛掉。

## 接上 Google Sheet（正式模式）

### 1. 建立試算表

新開一份 Google 試算表，從網址取得 ID：

```
https://docs.google.com/spreadsheets/d/【這一段是 ID】/edit
```

分頁**不用手動建**，系統第一次用到時會自己開好並寫上表頭。

### 2. 建立服務帳號

1. 進 [Google Cloud Console](https://console.cloud.google.com/) → 建立或選擇一個專案
2. 「API 和服務」→ 啟用 **Google Sheets API**
3. 「憑證」→ 建立憑證 → **服務帳號**
4. 進入該服務帳號 → 「金鑰」→ 新增金鑰 → **JSON** → 下載

### 3. 把試算表分享給服務帳號

打開剛下載的 JSON，找到 `client_email`（長得像 `xxx@yyy.iam.gserviceaccount.com`），
回到試算表按「共用」，把這個信箱加進去並給**編輯者**權限。

> 這步最常被忘記。沒分享的話 API 會回 403。

### 4. 設定環境變數

```bash
cp .env.example .env.local
```

填入 `GOOGLE_SHEETS_SPREADSHEET_ID`，並用三種方式之一提供憑證（詳見 `.env.example`）。
最省事的是把整包 JSON 貼進 `GOOGLE_SERVICE_ACCOUNT_JSON`。

### 換一把服務帳號金鑰（金鑰外洩時）

金鑰不小心被印出來、貼錯地方、或離職交接時，就換一把。
**順序很重要：先建新的、確認能用，最後才刪舊的**——反過來做網站會立刻掛掉。

1. **建新金鑰**
   Google Cloud Console → IAM 與管理 → 服務帳戶 → 點 `id-grandpa@prandpa.iam.gserviceaccount.com`
   → 「金鑰」分頁 → 新增金鑰 → 建立新的金鑰 → 選 **JSON** → 建立。
   瀏覽器會下載一個 `prandpa-xxxxxxxx.json`。此時新舊兩把都有效。

2. **裝進本機**（不用自己處理 base64）

   ```bash
   node scripts/set-credentials.mjs ~/Downloads/prandpa-xxxxxxxx.json
   npm run check:sheets     # 確認新金鑰連得上
   ```

   它會更新 `.env.local`，並把同一串 base64 另存成 `credential.b64.txt` 給你貼到 Render。
   這支程式不會把金鑰內容印出來。

3. **更新 Render**
   Render → 你的服務 → Environment → `GOOGLE_SERVICE_ACCOUNT_JSON`
   → 把 `credential.b64.txt` 的內容整份貼上去 → Save changes（會自動重新部署）。

4. **確認線上跑的是新金鑰**

   打開 `https://<你的網址>/api/health`，看 `credentials.keyId`：

   ```json
   "credentials": { "ok": true, "keyId": "3f9a1c22", "clientEmail": "id-grandpa@…" }
   ```

   `keyId` 是金鑰 ID 的前 8 碼。**變成新的那一串才算成功**，還是舊的就是 Render 沒生效。

5. **刪掉舊金鑰**
   回到 Cloud Console 的「金鑰」分頁，刪掉舊的那一把（對照金鑰 ID 前幾碼別刪錯）。
   刪完重新整理一次 `/api/health`，`ok` 仍是 `true` 就完成了。

6. **清掉暫存檔**

   ```bash
   rm credential.b64.txt
   ```

   下載的 `prandpa-xxxxxxxx.json` 也建議刪掉或收到密碼管理器裡。

試算表的分享設定不用動——服務帳號的信箱沒變，換的只是它的金鑰。

---

### 5. 驗證連線

```bash
npm run check:sheets
```

會依序檢查環境變數 → 服務帳號認證 → 試算表讀取 → 寫入權限，
並針對常見錯誤（沒分享、ID 打錯、金鑰失效）直接告訴你怎麼處理。
全部通過後重啟伺服器，首頁下方會變成「Google Sheet（正式）」。

> 本專案已用真實試算表完整驗證過：開場、入場、發放、階段切換、
> 伺服器重啟後資料仍在，以及 25 筆併發發放的正確性。

## 試算表長什麼樣

場次進行中會有這些分頁：

**`場次總表`** — 所有場次的索引
`場次代碼 | 場次名稱 | 狀態 | 目前階段 | 招募開放 | 彩池階段 | 彩池剩餘 | 開場密碼 | 建立時間 | 更新時間 | 聘書已發放 | 已封存`

**`{代碼}_玩家`** — 該場的玩家與目前數值
`玩家代碼 | 角色 | 角色代碼 | 通行碼 | 真實陣營 | 隱藏分支 | 分支已鎖定 | 勢力值 | 威望值 | 血量 | 剩餘抽取 | 持有技能卡 | 狀態 | 加入時間 | 更新時間 | 暱稱 | 聘書名次`

**`{代碼}_紀錄`** — 該場的流水帳，只新增不覆寫
`時間 | 類型 | 玩家代碼 | 角色 | 資源 | 變動 | 變動後 | 來源類型 | 事由 | 操作者 | 可公開`

**`{代碼}_舉報`** — 該場的舉報與判定結果
`舉報代碼 | 時間 | 舉報人代碼 | 舉報人 | 被舉報人代碼 | 被舉報人 | 線索卡 | 判定 | 已結算`

### 結束場次時會自動收斂

主持人按「結束」之後，上面那三個工作分頁會**彙整成一個以場次代碼命名的分頁**
（也就是當天日期），然後工作分頁就刪掉了。一場只留一個分頁，場次多了才找得到東西。

彙整分頁的內容分成四個區塊：

```
場次 / 名稱 / 開場密碼 / 最終階段 / 建立與結束時間
【玩家】  含暱稱、聘書名次與稱號、真實陣營、最終三種數值
【舉報】  每一筆的舉報人、被舉報人、線索卡、判定結果
【流水帳】完整的帳，不是只有最近 80 筆
```

寫入順序是「先寫彙整、成功了才刪工作分頁」，中途失敗最多是多一個分頁，
不會弄丟資料。

封存之後那一場就不能再進場、調配或重新開放了，密碼也會失效
（可以再拿去開新場）。

主持人可以直接在試算表上手動改數字，最慢 15 秒（`SESSION_CACHE_TTL_MS`）會反映到畫面上。

### 欄位定義改版時務必做的事

這個坑已經踩過三次：新增欄位後，改版前建立的場次會讀到錯位的主持通行碼，
**主持人再也進不去自己的場次**，而且不會有任何錯誤訊息。
其中一次是把中間某一欄換了意思（已調查次數 → 持有技能卡），
結果舊資料的數字被讀成技能卡代號，玩家手上冒出不存在的卡。

**新欄位一律加在最後面**，不要插在中間，也不要改既有欄位的意思。
`暱稱`／`聘書名次`就是這樣接在玩家表最後的，舊列讀起來自然是空值。

改欄位時要一起做三件事：

1. **讓 `rowToSession` 相容舊格式**（見 `src/lib/store/driver.ts` 的 `legacy` 判斷）
2. **在 `tests/schema.test.mjs` 補一個舊格式的案例**，把相容性鎖住
3. **更新 `scripts/migrate-sessions.mjs`**，讓既有資料能真正升級

```bash
npm run migrate:sessions            # 預覽會改什麼
npm run migrate:sessions -- --apply # 實際寫入
```

**遷移請在沒有人在玩的時候跑**，它會整批覆寫場次總表，跟進行中的場次搶寫會出事。

如果 `/api/health` 只抱怨「表頭是舊版」但資料都讀得到，那是純標題問題：
欄位是接在最後面的，程式照索引讀，不會錯位。跑一次遷移就會消失。

系統只會自動修「空分頁」的表頭；已經有資料的分頁一律不動——
只改表頭不搬資料會讓每一列整排錯位，比留著舊表頭更糟。
這種情況會由 `/api/health` 回報。

## 使用流程

**主持人**：首頁 →「我是主持人」→ **自訂一組開場密碼** → 開場
→ 把密碼唸給玩家 → 點選玩家 → 按快捷鍵發放
（勢力值 `+20/+50/+100`、威望值 `+1/+2/+3`）
→ 需要時切換階段、拍賣結算、發放聘書
→ 最後按「結束」，資料會自動彙整成一個分頁。

同一組密碼再輸入一次就回到那一場，不用記場次代碼。

**玩家**：首頁 →「我是玩家」→ **輸入主持人給的開場密碼** → 填暱稱並選角入場
→ 之後畫面每 3 秒自動更新。密碼錯誤或那一場已結束都顯示「無此場次」。

暱稱是聘書上的署名，入場時必填（20 字以內）。沒填到的可以在「我的」分頁補上；
聘書一發放就鎖住不能再改。

### 場次代碼與一天多場

主持人只輸入密碼，**場次代碼由系統用當天日期產生**：`2026-09-11`。
同一天再開一場就是 `2026-09-11-2`，以此類推——所以一天主持兩場不會打架。

這個代碼就是結束後彙整分頁的名字，也就是說一天一場時，
試算表裡就是乾乾淨淨一個以日期命名的分頁。

密碼只在場次還開著時有效。結束之後同一組密碼可以再拿來開新的場次。

## 技術架構

| 層 | 選用 | 理由 |
|---|---|---|
| 框架 | Next.js 16（App Router）+ React 19 + TypeScript | 前後端同一個專案，玩家用手機瀏覽器就能開，不必裝 App |
| 樣式 | Tailwind CSS v4 | 古風配色集中在 `globals.css` 的 CSS 變數，好整批換 |
| 資料庫 | Google Sheets API（服務帳號） | 依需求，100% 記錄在試算表 |
| 即時更新 | HTTP 輪詢（主持台 2.5 秒 / 玩家 3 秒） | 見下方說明 |

### 兩個關鍵設計

**1. 伺服器端快取，解決 Sheets API 配額**

Google Sheets API 的讀取限制大約是每分鐘 60 次。如果 20 個玩家每 3 秒輪詢一次，
就是每分鐘 400 次讀取，**必爆配額**。

所以場次狀態在伺服器記憶體裡保留一份快照：

- 玩家輪詢一律打在記憶體上 → 不論幾個玩家，對 Sheets 的讀取次數都固定
- 寫入（發放資源）即時寫回 Sheet，同時更新快照
- 快照超過 15 秒會在背景重新拉一次，順便撈到主持人手動改表的內容

因此「100% 用 Google Sheet 記錄」與「幾十個玩家同時看即時數字」可以並存。

**2. 每場次一把鎖，避免算錯數字**

發放資源是「讀餘額 → 加減 → 寫回」，主持人手快連按時可能交錯執行而少算。
`src/lib/game.ts` 的 `withLock()` 把同一場次的存取串成一條鏈。

**關鍵是：背景快取刷新也必須走這條鏈。** 否則會發生
「刷新讀到舊餘額 → 有人發放並寫回 → 刷新結果蓋掉快取 → 下一筆從舊值往上加」，
中間那筆就憑空消失了。這個 bug 在真實 Google Sheets 環境下實測時被抓到（帳本出現重複餘額），
已修正並用 25 筆併發驗證：帳本是完整的 1…25 序列，無重複也無遺漏。

> 這把鎖在單一 Node process 內有效。若之後要部署到會自動水平擴展的環境
> （多個實例同時服務），需要改成外部鎖，或固定跑單一實例。

**3. 批次寫入，讓全體發放維持在一秒內**

逐筆呼叫 Sheets API 每位玩家約 0.7 秒 —— 20 人全體發放要主持人在桌邊乾等 15 秒。
改成「餘額一次 `values.batchUpdate`、紀錄一次 `values.append`」後，
不論幾人都只有兩次往返：**實測 20 人從 15 秒降到 0.82 秒**。

**4. 配額重試**

Sheets API 有「每分鐘 60 次寫入」限制，主持人連續快速操作會撞到 429。
`src/lib/store/sheets.ts` 的 `withRetry()` 以指數退避重試，讓短暫尖峰自己消化掉，
而不是把錯誤丟給主持人。實測 25 筆瞬間併發全部成功（耗時 11 秒，因退避而拉長，但沒有任何一筆失敗）。

## 部署

### ⚠️ 不能用 GitHub Pages

GitHub Pages 只服務靜態檔案，**無法執行這個專案**：

- 專案有 9 個 API routes（`/api/sessions/…`），必須在伺服器上執行
- Google 服務帳號私鑰**必須留在伺服器端**。若改成純靜態、讓瀏覽器直接呼叫 Google API，
  等於把私鑰公開給每一位玩家——任何人都能竄改分數或刪掉整份試算表
- 伺服器端快取與寫入鎖活在 Node 程序記憶體中，沒有伺服器就沒有這兩者

同理，Netlify / Cloudflare Pages 的純靜態模式也不行。需要一個**能跑 Node 的環境**。

### 建議：Render（免費方案即可）

這個專案的鎖與快取都在單一 Node 程序內，最適合「一個長駐實例」的環境。
以下是完整步驟，第一次做也能跟著走完。

#### 步驟 0：先設定 GitHub 的預設分支

Render 預設會抓 repo 的 **default branch**。到 GitHub：

`Settings` → `General` → `Default branch` → 按旁邊的 ⇄ 圖示 → 選擇你要部署的分支 → `Update`

> 這跟 GitHub Pages 無關。Pages 不管設哪個分支都跑不動這個專案（見上方說明），
> 建議直接到 `Settings` → `Pages` 把它關掉，免得之後自己混淆。

#### 步驟 1：註冊 Render

到 [render.com](https://render.com) 用 **GitHub 帳號登入**，最省事，之後授權 repo 也順。

#### 步驟 2：建立服務

1. 右上角 `New +` → 選 **Blueprint**
2. 第一次會要你授權 GitHub。按 `Configure account`，選擇要開放的 repo
   （可以只授權這一個，不必開放全部）
3. 回到 Render，在列表中選這個 repo → `Connect`
4. Render 會自動讀取 `render.yaml`，顯示要建立的服務 `jiuye-yanglao`
5. 按 `Apply`

#### 步驟 3：填入兩個環境變數

`render.yaml` 裡這兩個變數標記為 `sync: false`，意思是「值不寫在程式碼裡，
由你在後台填」。Render 會直接跳出來問，或到服務的 `Environment` 分頁新增：

| 變數名稱 | 值 |
|---|---|
| `GOOGLE_SHEETS_SPREADSHEET_ID` | 你的試算表網址中 `/d/` 後面那一段 |
| `GOOGLE_SERVICE_ACCOUNT_JSON` | 服務帳號 JSON 檔的**完整內容**（從 `{` 到 `}` 全部貼上） |

> Render 的環境變數欄位支援多行，JSON 可以直接整包貼進去，不需要轉成 base64。
> 貼完記得按 `Save Changes`，它會自動重新部署。

#### 步驟 4：等部署完成

第一次建置大約 3～5 分鐘（要裝相依套件 + 建置 Next.js）。
在 `Logs` 分頁可以看進度，看到 `Ready` 或服務狀態變成綠色 `Live` 就完成了。

網址長得像 `https://jiuye-yanglao.onrender.com`。

#### 步驟 5：驗證設定正確

打開 `你的網址/api/health`，應該看到：

```json
{
  "ok": true,
  "storage": "sheets",
  "spreadsheetId": "1Zgu…qYuU（共 44 字元）",
  "credentials": "GOOGLE_SERVICE_ACCOUNT_JSON",
  "problems": [],
  "hint": "已連上 Google Sheet。"
}
```

**`storage` 是 `sheets` 就對了。** 如果是 `memory`，代表環境變數沒吃到，
`problems` 陣列會直接告訴你少了哪一個。這支端點只回傳布林值與遮蔽後的 ID，
不會洩漏金鑰內容，可以放心打開來看。

首頁最下方也會顯示目前模式，可以交叉確認。

#### 免費方案的一個特性

閒置 15 分鐘後服務會休眠，下一個請求要等約 50 秒冷啟動。
**活動開始前先打開網址讓它醒著**，之後只要持續有人使用就不會再睡。
（升級到 Starter 方案約 7 美元/月可以免除休眠，但辦活動前先開一次就夠了。）

### 其他選項

| 平台 | 適合度 | 注意事項 |
|---|---|---|
| **Render / Railway / Fly.io** | ✅ 最佳 | 單一長駐實例，架構完全吻合。`Dockerfile` 也已備好 |
| **Vercel** | ⚠️ 可用但有代價 | Next.js 原生支援、部署最快，但 serverless 多實例各有各的快取，玩家可能看到數字忽高忽低。若要用，把 `SESSION_CACHE_TTL_MS` 降到 3000 讓實例間快速收斂 |

| **GitHub Pages / 純靜態託管** | ❌ 不可行 | 見上方說明 |

### 部署後遇到問題怎麼查

| 症狀 | 先看這裡 |
|---|---|
| 首頁顯示「記憶體暫存」 | `/api/health` 的 `problems` 陣列，通常是環境變數沒填或拼錯 |
| 開場時跳 403 | 試算表沒有分享給服務帳號，或權限只給了「檢視者」 |
| 第一個請求很慢 | 免費方案冷啟動，正常現象，等約 50 秒 |
| 建置失敗 | Render 的 `Logs` 分頁；本機先跑 `npm run build` 確認能過 |
| 改了程式沒更新 | Render 預設會在 push 後自動重新部署，可到 `Events` 分頁確認有觸發 |

本機也可以先用 `npm run check:sheets` 確認憑證本身沒問題，再排除平台設定。

## 目前的限制

雛形階段刻意先簡化的部分，正式上線前建議處理：

- **身分驗證很陽春**：主持通行碼以明碼存在試算表，玩家身分存在瀏覽器 localStorage。
  正式版建議改成雜湊 + httpOnly cookie。
- **主持通行碼寫在試算表裡**：拿得到試算表的人就看得到。若要更嚴謹，改存環境變數或另一份權限更緊的表。
- **單一實例**：寫入鎖與快取都在記憶體，需固定跑一個實例（Render／Railway／自架都可以）。
  若要上 Vercel 這類會自動擴展的環境，得先把鎖改成外部實作。
- **一天一場**：場次代碼就是日期，同一天目前只能開一場。要一天多場的話，代碼規則要再擴充。
- **寫入配額**：Sheets API 每分鐘 60 次寫入。正常主持節奏（每分鐘數次發放）遠低於此，
  已有重試機制吸收尖峰；但若要做成「玩家自己觸發大量寫入」的玩法，就需要改成批次佇列。
